# 功能规格说明：NewAPI 登录入口兼容

**功能标识**: `newapi-login-route-compatibility`
**创建日期**: 2026-07-24
**状态**: v3 已实现，等待可见验收
**任务通道**: controlled
**需求版本**: v1
**确认记录**: 用户确认“确认执行 NewAPI 登录入口兼容 v1”

## 1. 目标与边界

- 背景：`nihao.dog` 的新版 NewAPI 前端使用 `/sign-in`，旧授权窗口固定访问 `/login`，导致客户端 404，关闭后又误报 `AUTH_CANCELLED`。
- 目标：在固定、同源的 `/login` 与 `/sign-in` 间实现可控兼容，并准确区分入口不存在与用户取消。
- 非目标：不新增任意入口配置；不改站点读取接口、余额/分组/价格、远程写入、自动登录提交或凭据存储方式。

## 2. 场景与验收

### 场景 1：新版 NewAPI（P1）

1. **Given** 站点明确/已检测为 NewAPI，**When** 用户点击网页授权，**Then** 优先显示 `/sign-in` 登录表单，不显示 `/login` 客户端 404。
2. **Given** `/sign-in` 明确为同源 404，**When** 存在旧版 `/login`，**Then** 仅回退一次。

### 场景 2：旧版与自动检测站点（P2）

1. **Given** 旧站仍使用 `/login`，**When** 用户授权，**Then** 保持原入口，不加载备用路径。
2. **Given** 首个同源候选呈现明确 404，**When** 备用路径也不可用，**Then** 主窗口显示尝试过的路径，不再误报用户取消。

## 3. 事项

### ITEM-001：兼容 NewAPI 登录入口

- 结果：NewAPI 优先 `/sign-in`、旧路径 `/login` 兼容；未知类型保持 `/login` 首选，仅对明确 404 尝试 `/sign-in` 一次。
- 验收：`nihao.dog/sign-in` 可见登录表单；路径选择/404 判定有单测；完整构建与本地测试包校验通过。
- 状态：executing。

## 4. 规则与异常

- 只允许在当前授权站点的同源固定路径 `/login`、`/sign-in` 间切换。
- 仅在当前候选路径且页面文本呈现明确 404 时回退一次。
- 用户主动关闭正常登录窗口仍显示“已取消网页登录授权”。
- 双路径不可用时使用可本地化的路由错误；不泄漏 URL 外的会话、Cookie、JWT、账号或密码。

## 5. 影响与假设

- 影响：主进程隔离授权窗口、renderer 错误提示、授权单测、本地测试 ZIP。
- 无数据迁移、无 IPC 新字段、无远端写入。
- 安全边界不变：令牌/Cookie/UA/密码仅留在主进程与 macOS 安全存储。
- 假设：新版 NewAPI 标准登录入口为 `/sign-in`；该假设已用 `nihao.dog/sign-in` 公开页面验证。其他第三登录路径不纳入本次。

## 6. v2：NewAPI 会话回传修复

**需求版本**: v2
**确认记录**: 用户确认“确认执行 NewAPI 会话回传修复 v2”

- 背景：`nihao.dog` 已通过 `/sign-in` 登录并进入后台，但授权窗口未自动关闭，也未保存站点。NewAPI 将短期访问令牌保留在页面内存，刷新 Cookie 属于隔离授权分区。
- 目标：授权成功后，主进程仅通过该临时授权分区、同源固定刷新接口恢复标准 AuthBundle，保存站点并清理临时窗口和分区数据。
- 验收：用户在 `nihao.dog` 登录后，无需复制 JWT、Cookie 或密钥；应用自动关闭授权窗口，将站点保存为 NewAPI 三方站点，并开始同步。
- 安全边界：不向 renderer、日志、错误文本、测试快照或规格记录写入账号、密码、Cookie、JWT、响应原文。刷新请求仅能访问当前站点的 HTTPS 同源路径。
- 非目标：不读取页面内存令牌，不新增任意远程地址或路径，不修改 NewAPI 远端数据、站点角色、读取适配器或已有持久化格式。

## 7. v3：NewAPI 页面内同源会话恢复

**需求版本**: v3
**确认记录**: 用户回复“ok”，确认执行 `NewAPI 页面内同源会话恢复 v3`

- 背景：`nihao.dog` 已通过 `/sign-in` 进入登录后控制台，但 v2 的隔离分区刷新仍未产生可保存的标准授权结果，授权窗口继续停留，主界面也未新增站点。
- 根因证据：本地 NewAPI 源码显示标准客户端以浏览器页面会话调用固定的 `POST /api/user/auth/refresh`；该路径依赖登录页面上下文、同源 Cookie 与会话约束。当前桌面端主进程分区请求已携带分区凭据，但在真实站点未恢复成功。
- 目标：保留 v2 的分区刷新作为首选；只有它未恢复令牌时，才在已登录且同源的授权页面中调用固定刷新接口，并仅将标准响应 `success: true` / `data.access_token` 交回主进程用于既有加密保存。
- 验收：用户登录 `nihao.dog` 后，授权窗口自动关闭，主界面出现 NewAPI 三方站点并开始同步；无需复制 JWT、Cookie、页面响应或密钥。
- 安全边界：主进程先校验当前页面与刷新地址同源且为 HTTPS；页面脚本只能调用固定的站点同源刷新路径、禁止重定向和任意 URL；只接收受限的字符串令牌字段；不记录、显示、持久化或向 renderer 传递 Cookie、页面文本、账号、密码、会话对象或原始响应。
- 非目标：不读取 React/Zustand 页面内存、不模拟登录提交、不新增远程写入、不改变已保存站点和 NewAPI 只读适配器能力。

## 8. v4：OneAPI Cookie 会话授权修复

**需求版本**: v4
**确认记录**: 用户确认“确认执行 OneAPI Cookie 会话授权修复 v4”

- 背景：真实 `nihao.dog` 公共前端在密码登录后以浏览器 Cookie 调用 `/api/user/self`，随后才将返回的用户资料写入 `localStorage["user"]`。它不实现 v2/v3 假定的 `POST /api/user/auth/refresh`，该路径实测返回 404。因此 v3 即使打开了正确登录入口，也始终等不到 Bearer Token，授权窗口不会保存或关闭。
- 目标：保持标准 NewAPI 的刷新-token 路径不变；仅对明确不支持刷新契约的 HTTPS 同源 OneAPI 兼容站点，在用户离开登录页后用隔离 BrowserWindow 分区的固定 `/api/user/self` 进行只读会话验证。验证成功时只加密保存必要 Cookie、UA 和内部会话模式，并让 NewAPI 读取客户端可用 Cookie-only 会话访问固定读取接口。
- 验收：用户在 `https://nihao.dog/sign-in` 成功登录后，应用自动关闭授权窗口、保存/更新站点并同步余额、分组、价格及令牌列表；Cookie-only 站点不再循环调用不存在的刷新路径；会话失效时显示原有重新授权路径。
- 安全边界：禁止读取完整 `localStorage` 用户对象、页面框架状态、Cookie/JWT 原文、账号、密码、余额或响应原文；验证仅接受 HTTPS 同源固定 profile 路径的成功布尔结果；Cookie 与 UA 仅经既有 `safeStorage` 留在主进程，绝不跨 IPC、日志、测试快照或错误文本。
- 非目标：不修改远端业务数据、管理员权限、站点角色、NewAPI 只读能力范围、登录表单、自动填表策略、Git 远端或 GitHub Release。

## 9. v5：站点智能接入与安全保活体验修订

**需求版本**: v5
**确认记录**: 用户确认“确认需求与影响 v5”
**状态**: 已确认并实施完成，等待用户验收

### 已确认根因

- 当前“自动检测”实际需要用户额外点击“自动识别/自动探测”，且诊断把非 JSON 的 HTTP 200 页面也视为有效接口信号，可能让 NewAPI 与 Sub2API 信号冲突，最终不输出站点类型。
- 对 `nihao.dog` 的无凭据只读检查显示：`/api/user/self` 与 `/api/user/self/groups` 返回 JSON 401，`/api/v1/groups/available` 返回 JSON 404；这应被识别为 NewAPI，而不是未知类型。
- 当前保活只在快照返回未授权后尝试，失败统一显示“上次保活未完成”；应用退出中断、网络可重试、验证码/2FA、密码失效等状态没有可行动区分。
- 添加表单同时暴露“API 地址”和“API 基址”，并默认展开诊断与路径字段；正常站点需要理解内部接口根路径才能完成添加，超过了默认流程的必要复杂度。

### ITEM-007：真正自动的站点类型识别

- 结果：用户输入一个站点地址后，系统自动发起无凭据、只读、可取消的诊断；识别成功即应用适配器类型和默认接口根/路径，无需先手动点诊断。
- 规则：只有结构有效的 JSON 响应，或 JSON 401/403，才能作为接口信号；HTML/登录页/反代 200 不得作为成功信号。用户粘贴 `/keys`、`/login`、`/sign-in` 等页面路径时，识别使用同源站点根；Sub2API 的明确 `/api/v1` 根仍保留。
- 失败回退：探测失败时保留“自动”，在同一处显示原因与 Sub2API / NewAPI / 自定义的手动选择；不会猜测任意 API 路径，也不会自动携带已保存 Cookie、JWT 或密码。
- 验收：`https://nihao.dog` 与 `https://nihao.dog/keys` 在未登录状态可识别为 NewAPI；HTML 200 不误判；用户手动选择类型后自动结果不覆盖选择。

### ITEM-008：保活状态语义与恢复可见性

- 结果：把笼统“上次保活未完成”替换为可行动状态：会话正常、正在恢复、等待网络重试、需要人工验证、凭据失效、应用退出中断；状态显示完整时间和下一步。
- 规则：启动时把遗留的“正在恢复”归为“上次应用退出中断”，不伪装为仍在运行；人工验证、验证码/2FA、风控或密码失效均停止自动提交并展示授权入口。
- 验收：每种状态都有明确文案、颜色以外的文字/图标和相应操作；重新打开应用后不存在永久“正在尝试重新登录”的假状态。

### ITEM-009：用户显式开启的安全自动保活

- 结果：仅在用户保存账号密码并开启“自动保活”后启用。正常轮询继续优先令牌刷新；Cookie-only 或刷新失败的站点仅在确认会话失效后进入保活队列。
- 规则：应用内一次只运行一个自动登录窗口；其余站点排队，不会静默丢弃。网络/超时使用受限退避（1、5、30 分钟，最多 3 次）；验证码、2FA、风控、密码错误和站点契约不匹配不自动重试。用户可手动“立即检查”触发同一受控流程。
- 安全边界：自动检测不使用保存的凭据；保活只访问站点 HTTPS 同源登录页；不绕过挑战、不新增远端业务写入、不向 renderer/日志返回密码、Cookie、JWT 或页面原文。
- 验收：同站重复未授权不会并发弹多个授权窗；网络失败按节奏重试；人工挑战停止队列并把窗口带到前台；成功后立即重刷快照并更新“会话正常”。

### ITEM-010：默认简单、按需高级的添加站点流程

- 结果：默认表单只保留“站点地址”“显示名称（可选，默认取域名）”“站点角色”“智能识别结果”和“网页登录授权”。“API 基址”改名为“接口根地址（高级）”，连同路径、JWT 备用、管理员凭据和适配诊断收进可展开的高级配置。
- 规则：标准 Sub2API 自动推导 `/api/v1`，NewAPI 自动使用站点根，已识别的 lcodex 继续使用其兼容根；只有探测失败、站点处于子路径或用户主动打开高级配置时，才显示/允许覆盖接口根地址。
- 验收：新用户只输入 `https://nihao.dog` 即可看到 NewAPI 结果并点击网页登录授权；不出现并列的“API 地址/API 基址”；已有二开站仍可在高级配置完整覆盖根地址和路径。

## 10. v6：NewAPI Cookie 会话落盘

**需求版本**: v6（本次确认包名：`NewAPI Cookie 会话落盘 v1`）
**确认记录**: 用户确认“确认执行 NewAPI Cookie 会话落盘 v1”

- 背景：部分 OneAPI 兼容站点登录后可通过同源 Cookie 成功读取 `/api/user/self`，但刷新接口可能是 404、403、405 或非标准响应。旧逻辑把 Cookie 会话保存依赖于“刷新接口明确 404”，导致网页已登录却未落盘，后续快照报“未配置 NewAPI 登录会话”。
- 目标：当授权窗口已经离开固定登录页、保持 HTTPS 同源且固定 profile 验证成功时，保存受限 Cookie 会话；刷新接口仍保留为标准 NewAPI 的优先恢复方式，但不再是 Cookie 保存的前提。
- 验收：OneAPI 的 profile 验证成功且 Cookie 合法时，窗口自动关闭、站点保存并开始同步；登录页不误报会话失败；关闭一个已进入后台但无法落盘的窗口时给出可行动中文提示；设置页只显示 `JWT 已保存`、`Cookie 会话已保存` 或 `未授权`，不显示原文。
- 安全边界：固定 HTTPS 同源 profile、隔离 BrowserWindow partition、Cookie 长度/格式校验、主进程安全存储；renderer 只接收布尔状态；不读取或记录 Cookie/JWT/账号/密码/Profile 响应体。
- 非目标：不更改远端站点、不绕过验证码/2FA/风控、不新增任意路径、无需用户粘贴 API Key。

## 12. v8：OneAPI 选中用户上下文兼容

**需求版本**: v8（用户授权“确认，一直到成功，过程不要给我确认”）

- 背景：`nihao.dog` 公开网页客户端会从同源页面的 `localStorage.uid` 读取一个选中用户编号，并对 `/api/user/self` 等请求附加 `New-Api-User`。桌面端只带 Cookie 验证该接口，导致网页后台可用而会话捕获失败。
- 目标：仅在已经验证为 HTTPS 同源、非登录页的 Cookie-only OneAPI 授权流程中，读取并校验单个 1–20 位数字 `uid`；该值只用于同源 profile 验证和后续 Cookie-only 只读请求。
- 验收：登录后 profile 验证带与网页一致的选中用户头；站点自动关闭授权窗、加密保存 Cookie 与该受限上下文并开始同步；切换为 JWT/refresh-token 时该上下文被清除。
- 安全边界：不读取任意 localStorage 键、完整 `user` 对象、Cookie/JWT/密码或 profile 响应体；该值不跨 IPC、不显示、不写日志，仅以安全存储加密保存；非数字、过长或跨域值拒绝；无远端写入。
- 回退：删除 Cookie-only 的受限上下文路径即可恢复 v7；旧站点数据保持可读。

## 13. 数据与刷新安全修复及自定义 API 根编辑 v2

**需求版本**: v2

**确认记录**: 用户确认“确认执行 数据与刷新安全修复及自定义 API 根编辑 正式实施包 v2”

- 背景：本地站点与偏好文件一旦损坏，旧读取路径可能将它视为新空文件并在下一次写入时覆盖唯一原件；轮询与用户点击刷新并发时，旧异步结果可能覆盖较新结果；自定义兼容模板缺少可编辑 API 根，导致二开站无法把请求从默认 `/api/v1` 切换到同源的实际根。
- 目标：损坏文件只能在成功备份原件后才回退为空；用户发起的刷新必须强制产生新请求意图，旧请求不得提交快照、关联、账本或事件；自定义兼容允许编辑、预览并保存 HTTPS 同源 API 根。
- 验收：备份失败时任何读改写都会报错且原文件不变；成功备份后保留 `.corrupt-*` 原件；手动刷新会使旧轮询失效；`https://www.krill-ai.net/api` 在自定义兼容保存后仍保持该值；HTTP、跨域、带凭据、查询参数或片段的根地址被拒绝。
- 安全边界：读取映射仍为主进程中的同源 HTTPS GET；预览只使用已保存的主进程凭据，不传递令牌、Cookie、密码或响应原文给 renderer；无远端业务写入。
- 非目标：不猜测或探测真实二开站的私有接口，不改动真实站点配置，不放宽跨域 API 调用，不打包、发布或推送。

### ITEM-014：本地数据文件安全恢复

- 状态：completed。
- 结果：`stations.json` 与 `ui-preferences.json` 解析失败或顶层结构错误时先重命名为 `.corrupt-*`；若重命名失败，读取和后续写入均失败，原文件不被覆盖。

### ITEM-015：刷新意图与过期提交隔离

- 状态：completed。
- 结果：手动刷新与保活检查使用强制刷新意图；旧轮询在令牌轮换、管理员账号指纹、快照、来源关联、账本和事件提交前都校验当前 epoch。

### ITEM-016：自定义 API 根编辑

- 状态：completed。
- 结果：接口适配中心在“自定义兼容”模板下提供 URL 输入，草稿 API 根同时参与检测和保存；显式填写的同源根不再被旧默认值归一化逻辑覆盖。

## 14. 接入与涨跌可见性 正式实施包 v1

**确认记录**: 用户确认“确认需求与影响 v1”及“确认执行 接入与涨跌可见性 正式实施包 v1”。

### 目标与边界

- 让已经持久化的真实倍率涨跌同时出现在价格榜、近期分组变化和系统通知中；通知点击后直接打开对应的近期变化窗口。
- 只为 Aihub、Krill AI、Zanzhu 增加经确认的只读兼容。不会猜测其他二开接口、读取真实站点凭据或修改远端数据。
- 不新增发布、打包、远端写入、通用跨域探测或用户资料/令牌向 renderer 的传递。

### ITEM-017：涨跌记录与通知可见性一致

- 结果：主进程只对本次成功写入的 `rate-up` / `rate-down` 事件发出无敏感偏好更新和原生通知；首次观察仍只建立基线，不产生通知。
- 交互：点击仅包含涨价或降价的通知时，近期分组变化窗口预选该方向；混合通知预选“全部”，不遗漏任一方向。
- 验收：重启后历史仍由本地持久化偏好读取；价格榜/近期变化读取同一事件源；重复轮询不重复通知。

### ITEM-018：Aihub 受控兼容诊断

- 结果：在默认用户信息路径未被手工覆盖时，Aihub 使用已知只读 `/auth/me?timezone=Asia%2FShanghai`；手工路径始终优先。
- 验收：诊断与快照使用同一默认路径，不把 HTML、跳转或风控页误判为可用 JSON。

### ITEM-019：Krill AI 受控兼容

- 结果：Krill 默认读取 `/api/auth/me`、`/api/credits`、`/api/my/channels`；旧的同源 `/api/v1` 根仅会在 404 时尝试站点根，不改写用户保存的根或路径。
- 降级：余额可读而分组接口不可读时，快照保持健康并明确显示“余额已读取，但分组暂不可读取”；未授权、重定向、网络错误仍是错误状态。

### ITEM-020：Zanzhu API 根别名兼容

- 结果：仅 `zanzhu.denxio.com` 到固定 `api.denxio.com` HTTPS 别名允许在 404 时作为只读候选；Referer 跟随当前候选根。
- 非目标：不对任意站点开放跨主机回退，不修改或保存探测到的别名根。
