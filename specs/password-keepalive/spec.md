# 功能规格说明：站点密码保活

**功能标识**: `password-keepalive`
**创建日期**: 2026-07-23
**任务通道**: controlled
**需求版本**: v1（已确认执行）

## 目标

三方站点与我的站点共用一套本地加密的网页登录凭据。站点会话失效时，应用先沿用现有 `refresh_token` 续期；仅当续期失败且明确是未授权/会话失效时，才在同源 HTTPS 登录页尝试自动重新登录，并保存新令牌、Cookie 与 UA。

## 事项清单

- `ITEM-001`：提供默认关闭的“令牌失效时自动重新登录”站点配置，仅允许已保存账号密码的 HTTPS 站点开启。
- `ITEM-002`：实现刷新令牌优先、自动登录兜底的保活链路，并限制同一时间只运行一个授权窗口。
- `ITEM-003`：验证码、短信/邮箱验证码、2FA、WebAuthn、风控页或无法安全识别的表单必须转为人工授权，不得绕过。
- `ITEM-004`：记录不含敏感数据的保活状态，增加凭据边界与开关行为的回归测试。

## 业务规则与边界

- 登录账号、密码、访问令牌、刷新令牌与 Cookie 只保存在主进程的 macOS 安全存储；渲染进程只获得“已保存”与保活状态。
- 自动提交仅限保存站点的 HTTPS 同源页面，且页面具备明确账号、密码和登录提交控件。
- 失败后冷却 5 分钟；同一站点不并发，所有站点共用一个隔离授权窗口，避免重复提交和风控放大。
- 手动“重新授权 / 换号登录”与“使用保存账号密码授权”保持可用。清除本地登录凭据会一并关闭自动保活。
- 不保证所有二开站点都支持自动登录；要求人工验证的站点由用户完成验证后，应用再捕获新会话。

## 验收标准

1. 保存账号密码并开启保活的三方或我的站点，在会话失效后会先尝试刷新令牌，再尝试自动重新登录。
2. 成功后新令牌和会话信息加密保存，后续同步恢复；密码、JWT、Cookie 不出现在 UI、日志、测试断言或 Git。
3. 识别到安全挑战时显示预填登录窗口并标记“需要人工完成验证”，不自动绕过挑战。
4. 无保存凭据、非 HTTPS、连续失败冷却中、已有授权窗口时，不会启动自动提交。
5. 清除保存凭据后，自动保活同步关闭。

## 非目标

- 不自动处理验证码、短信、邮件、2FA、WebAuthn 或 WAF 挑战。
- 不新增远程管理写入、不改变分组、价格、余额、成本或收益计算。
- 不在浏览器预览模式执行网页登录授权。
